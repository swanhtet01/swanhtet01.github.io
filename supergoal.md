## Objective

Bring SuperMega.dev to a sellable, founder-controlled Shop launch built around a fast, reliable installed app, supported by a useful browser companion and internally managed Sites and Commerce. A merchant should be able to start selling on a tablet or PC, scan products, finish a sale, find its receipt again and recover from a printer, network or power interruption without guessing what happened. Prove one account and workspace boundary across devices, honest sync/backup and restore, role-based administration, and a public download path tied to a verified build. Use maintained open-source software as a capability and R&D supply chain. Match the accepted premium design standard in the real app, not only in website captures; maintain source-bound CI, security, device and performance evidence before an independently reviewed production release.

The differentiated promise is a full English or full Burmese merchant experience that removes catalog setup, checkout and insight work while keeping money and stock explainable. AI should accelerate reviewed catalog import and grounded decisions, within consent, privacy, quality and cost limits. After customer-facing acceptance, package one complete Basic/Free offer, a capability-backed Pro offer and Assisted Launch, then build measured onboarding, sales and marketing operations and cost-controlled agents on existing paid cloud/VPS capacity.

For sample catalog photography, source real product/package images online first and record the exact item, pack-size evidence, source URL, file digest and photo credit/license. Public website captures must use rights-cleared product photos or merchant-owned photos; an accessible retailer image is not a reuse license. The current synthetic fixture has one CC BY-SA 3.0 MAMA photo and four retailer photos without a verified commercial reuse grant. Because this repository is public, the four files are already distributed as source assets; replace or remove them before commercial release, and keep the gallery publication gate closed. Do not replace a recognizable package with an unrelated generated approximation or claim an unreadable size was visually verified.

The current design decision uses an **eliminate / reduce / raise / create** test against a merchant's first day. Eliminate repeated device-only warnings, dummy controls and manual message re-entry from the primary path. Reduce setup to a usable first catalog item, a first sale and an optional connected-account step; move printer, wallet, team and advanced policy setup to the point of need. Raise sale/stock correctness, discoverability, full-language quality, hardware reliability and recovery to non-negotiable release criteria. Create a reviewed photo-to-catalog path and later grounded, cited sales/stock suggestions that save measured operator time. Do not add an AI card, setting or subscription control unless it improves a named job and its failure state is clear.

## AI-native operating model

**Working autonomously, scaling infinitely** is the direction for SuperMega's internal workcell, not a claim of unlimited compute or unattended authority. The outcome is less time and cost from a real merchant problem to a verified improvement. Agents should use other AI for bounded research, generation, critique and test-case discovery, while tools and source records establish what actually happened. Give them machine advantages a human team cannot sustain manually: exact-revision memory, repeatable multimodal inspection, many cheap hypotheses, replayable failure cases and continuous measurement. Spend concurrency only when independent tasks and measured throughput justify it; keep one accountable integration writer.

The operating loop is **observe → propose → implement → verify → learn**. Each work order names one user job, exact input/source revision, permitted tools and data, owner, budget, expected artifact, deterministic acceptance check, evidence type and stop condition. A second model may challenge a proposal or generate counterexamples, but cannot approve its own output. Record tool traces and outcome metadata without raw secrets or customer content. Turn each confirmed failure into a reproducible test or narrow skill update, replay the relevant evaluation set before changing prompts, models or tools, and retire changes that do not improve the merchant outcome. Use the existing work-order and evaluation system; do not launch a parallel agent platform.

Measure the machine advantage on the **same pinned cases**: manual/current workflow, one agent, and a bounded proposer-plus-challenger workflow. Blind-check factual accuracy and task completion first, then compare operator corrections, elapsed time, retries and cost per accepted result. Use multimodal input, exhaustive edge-case generation and exact-revision replay where they demonstrably outperform a human-maintained checklist. An agent's own confidence, a second model's agreement, or four checked boxes is never proof that a blocked or partial job completed. Stop an experiment when it adds cost or complexity without a repeatable merchant or operating gain.

The first internal deployment target is the approved paid VPS/cloud capacity. Prove one queued, authorized, bounded synthetic job survives worker restart, yields a source-bound artifact and independent evaluation, records model/tool cost, and never performs an unapproved external write. Until that end-to-end proof exists, agent execution is **NOT RUN** as a hosted capability. Local runner RAM checks do not determine hosted readiness. The [AI-native operating loop](docs/ai-native-operating-loop.md) holds the first benchmark, task contract and acceptance matrix; the launch-control record holds mutable evidence.

## Product promise and boundaries

- **Shop** is primarily an installed app for Android tablet, iPad and Windows PC. It helps a business sell at the counter, manage products and stock, complete orders, record payments honestly, find completed sales and receipts, and close work with useful records and reports. The browser companion serves account, workspace, team, plan, backup, reporting and support tasks as those capabilities become real; daily checkout must remain usable offline.
- **Sites** helps a business publish clear pages, keep business information current, and receive and follow up on genuine inquiries. Its generated address must keep working across published updates; an optional custom domain requires server-verified ownership, DNS, HTTPS and route checks before reversible activation.
- **Commerce** helps a business publish a catalog, receive online requests or orders, and track the supported payment and fulfillment steps.
- Retain Plant records and recovery without adding it to the current customer-acquisition path. SOL is a separate build; its code, infrastructure and customer data are outside this Shop-first launch.
- `supermega.dev` explains the real capabilities and leads to one clear Shop login or contact route. `app.supermega.dev` gives customers their authenticated Shop workspace. Sites and Commerce editing, setup and management remain restricted to authorized internal operators at both the UI and API layers; hiding navigation alone is insufficient. Keep public storefront and customer-review routes available within their existing validated boundaries. Custom work and R&D are clearly separated from generally available products.
- The public Shop page should show the app working at realistic PC, tablet and phone sizes, state which platforms actually have installable verified builds, and provide a clear download or sign-in path. A screenshot or unsigned QA archive is not a public installer. Do not advertise Windows, multi-device, cloud backup, AI or payments as ready from a source-only implementation.
- Account sign-in must create or select the right Shop workspace without bringing another business's data into view. Keep local checkout available through an explicit offline path; attaching local records to an account requires reviewed ownership, deduplication, conflict handling and recovery. The server owns membership, role and subscription entitlements. Admin settings and billing are visible only to authorized roles; a cached entitlement never grants a new metered AI or team action while offline.
- Do not expose trial, setup, demo, sample or reset flows as the primary public experience. Private, isolated synthetic fixtures remain valid for engineering and must be labelled as synthetic.
- Connected messaging must put new customer messages into the authenticated Shop inbox automatically; staff must not have to paste messages. A channel event is an inquiry until an operator verifies extracted customer, item, quantity, payment and fulfillment details. Never convert a message into a confirmed order or send an automatic reply without explicit supported policy and acceptance.
- Treat internal Ecommerce-to-Shop arrivals and external social-message connectors as separate capabilities. A visible Ecommerce inbox does not prove Messenger, Instagram, Viber or other channel connectivity. For external connectors, require verified signatures, tenant/page mapping, durable idempotency, bounded payloads, retention controls and observable delivery state before claiming receipt.
- Showcase imagery must come from the current, running platform at the exact source revision being represented. Do not present generated mockups, stale screens, blurred crops or a second capture of the same screen as working features.
- Serve a broad small-business audience. Use concise English product language where it improves clarity, then validate Burmese onboarding and operational wording with actual users. Myanmar context and payments matter where supported; do not imply automatic KBZPay, WavePay, settlement or delivery behavior without working, verified integrations.

## Completion sequence

### 1. Establish source truth

At the start of a slice, verify branch, commit, worktree state, active server and applicable current instructions. Read the current launch checkpoint and relevant product evidence. Keep one writer and one bounded objective. Preserve unrelated user work and do not repeat unchanged checks.

### 2. Complete Shop for a real operator

Start with the fast counter journey: find or scan a real item, set quantities, calculate the exact total, record the chosen payment method, confirm once, and produce a retrievable sale and receipt. Keep catalog setup to one review and one clear commit action; require a separate confirmation only where a managed/server-side write needs it. Build and test distinct touch and keyboard layouts on Android tablet, iPad and Windows PC. A generated or unsigned Windows QA package is an engineering candidate until the runner, brand, signing, installer, update and device tests are accepted. Make inventory, receiving, stock counts, returns, close and reports reliable and explainable. Test scanner focus, narrow screens, stale stock, duplicate actions, reload and recovery. Verify a physical barcode scanner and receipt printer on actual supported hardware before claiming compatibility. Treat offline operation as incomplete until queued changes, conflict handling, server acknowledgement, backup restore and cross-device recovery are tested.

### 3. Complete internal Sites and Commerce end to end

For authorized internal operators, verify Sites business setup, page editing, preview, publish, stable URL across updates, contact capture, inquiry follow-up, metadata and save/reload. Increase page/template capacity only after the frontend, runtime, database and storage limits agree and a maximum-content Burmese site survives the full workflow. For internally managed Commerce and its public storefront, verify catalog accuracy, availability, customer request or order capture, operator review, payment-status recording, fulfillment and customer receipt. Keep customer requests distinct from confirmed orders, recorded payment distinct from settlement, and intended delivery distinct from completed delivery. Test retries, double submits, stale inventory, failure states and recovery. Do not offer customer access to either internal editor without a later founder decision and separate acceptance.

### 4. Prove account and data boundaries

Use the official managed sign-in and founder identity. Verify membership discovery, correct workspace selection, authorized reads and writes, save/reload, interrupted-session recovery, sign-out and denial across a second user or workspace. Prove that an ordinary customer cannot enter Sites or Commerce management through navigation, direct URLs or API calls, while the supported public storefront and customer review still work. Bind every check to the exact application build and backend. Prefer synthetic acceptance data in a non-production target. Do not create users, change access, write to a managed database or alter provider configuration without authority for the exact target, operation and expiry.

### 5. Match the public presentation to the product

Use a consistent light white, graphite and cobalt design with strong hierarchy, useful task-focused density, calm spacing and responsive behavior. Remove unnecessary buttons, duplicated explanations and exposed implementation choices. Explore substantial interface changes visually, then implement the chosen direction in the real app. Keep shared patterns and product-specific tasks coherent. Capture screenshots from each actual product route and label their source, version and record type. Confirm every public feature claim against implemented behavior.

### 6. Establish a sellable offer and delivery system

After product workflows are accepted, define one complete Basic/Free offer, a Pro tier containing only shipped and supported capabilities, and a clearly scoped Assisted Launch service. The working entitlement hypothesis is: Basic covers a trustworthy single-shop sales, catalog, stock, receipt and data-export path; Pro adds only proven multi-device/team operations, advanced reports and a bounded monthly AI allowance; Assisted Launch covers merchant catalog import, device/printer setup and training. Core data retrieval and recovery must never become a surprise paywall. Test costs, usage limits, support load, payment operations and regional fit before pricing or publishing tiers. Build a simple lead-to-delivery record with owner, need, scope, quote status, onboarding, acceptance and follow-up. Keep drafts private until public communication is authorized. Do not contact prospects or customers without specific authority.

### 7. Build from an open-source capability supply chain

Use open-source projects as a first-class source of product capability, R&D leverage and operating tools. Select the right mode for each capability—use a development tool, adopt a library, self-host a service, or maintain a narrow fork—rather than installing every repository or copying a whole product indiscriminately. Treat upstream software as the engine; SuperMega's product value is the cohesive, reliable, Burmese-first workflow that connects merchant work, local channels, devices, useful insights and accountable agents.

- **Investigate behavior:** the exact project is [morluto/rea](https://github.com/morluto/rea); its CLI package is `rea-agents`, and `reverse-engineer-anything` is only the bundled skill name. Pin the tested release in each adoption record and use it for one authorized shipped-artifact or passive public-site question when source alone cannot answer. Prefer the local CLI; skill installation does not mean this session has REA MCP tools. Keep raw evidence local, label observations/inferences/tests/unknowns, respect resource limits, and treat partial graphs as evidence rather than recovered source or product specifications. Rebuild useful outcomes in SuperMega; do not copy protected source or assets, analyze ordinary source as if it were REA, or change global MCP configuration as a side effect.
- **Improve interface quality:** use [Impeccable](https://github.com/pbakaus/impeccable) for UX/design critique, visual iteration and deterministic frontend checks. Treat its findings as evidence to review, not an automatic design decision; preserve SuperMega's product context and accepted visual direction.
- **Run agents:** evaluate [Agent Substrate](https://github.com/agent-substrate/substrate) or comparable runtimes for isolated, resumable, scale-to-zero workers against existing paid cloud/VPS capacity. It is pre-1.0 and Kubernetes-based, not a lightweight VPS agent daemon. Prefer the already-supported hosted queue/worker or a simple existing VPS deployment; add cluster operations only when measured concurrency or sandbox requirements justify them. Compare security boundaries, cold-start, utilization, reliability and total cost.
- **Create brand and product media:** evaluate StoryTold's [ArtCraft](https://github.com/storytold) suite (including [PhotoCraft](https://github.com/storytold/photocraft)) for internal marketing, documentation and product-asset workflows. PhotoCraft is early alpha. Verify the exact code license, bundled artwork/fonts, brand terms, release, supported devices and reproducibility separately; do not make an alpha editor a production dependency without a passing trial.
- **Other capabilities:** assess candidate projects such as Supabase, PostHog, NocoDB, n8n, Plausible, Listmonk, Cal.com, Documenso, Penpot, Excalidraw and Dify against a defined gap. Prefer a focused upstream integration over a redundant internal clone when it lowers cost without weakening product quality, privacy or control.

For every adoption, record repository and immutable revision, license for code/dependencies/content/brands, maintenance and security posture, data and network boundaries, integration and operating cost, user-visible value, measurable acceptance test, upgrade/rollback plan and exit path. Prototype on synthetic data with a fixed time and resource budget, compare against the current/manual workflow, then adopt, defer or reject with evidence. Keep the selected catalog short and current. Represent internal agents as evaluated roles and repeatable workflows with owners, input boundaries, tools, outputs, retries and human gates—not as claims that unstaffed agents are employees. Run agent workloads on existing paid cloud/VPS capacity with scale-to-zero defaults; local inference is out of scope. Inspect Contabo or another VPS only through authorized access and measured workload/cost comparisons. Do not route to metered model APIs without explicit approval for the provider, task and spend ceiling, and do not duplicate CRM, identity, job queue or evidence systems.

## Engineering and operating standard

- Keep presentation, business rules, persistence and provider integrations separated at meaningful boundaries. Use typed contracts, server-side validation, explicit state transitions, tenant-scoped access, idempotency, bounded retries, audit evidence and actionable errors.
- Make the common path short: one primary action, useful defaults and versioned templates. Keep advanced controls available to authorized operators without placing them in first-use tasks. Extend page sections and product workflows through bounded, versioned schemas and explicit capability contracts, with migration and rollback tests; never advertise unlimited customization when a renderer or backend supports only a fixed set.
- Preserve money and inventory correctness under duplicate, stale, partial-failure and recovery cases. Add migrations with compatibility and rollback plans. Test backup restoration rather than relying on backup existence.
- Measure build size, real-user flow latency, failure rate and recovery time on representative lower-resource devices and networks. Performance caps are release contracts; update them only with an evidence-backed decision.
- Prefer maintained first-party documentation and reproducible incumbent workflows for competitive research. Distinguish public claims, hands-on trials, synthetic tests, local behavior, immutable previews, hosted acceptance and customer acceptance.
- Before a substantial redesign, name the user, task, start state and successful outcome; review the current journey, create visual alternatives, select against usability/accessibility/device criteria, implement the real task and verify all relevant states. Screenshots are evidence of appearance only, not working behavior.
- Keep an app capability matrix for Android tablet, iPad, Windows PC and browser: build/install, catalog import, scan, printer, wallet, offline sale, sale history, sync, restore, admin and AI. Each cell needs `PASS`, `FAIL`, `BLOCKED` or `NOT RUN`, a device/build and evidence. A common Flutter source file does not prove equal platform support.
- Treat AI as a reviewed assistant: suggest products from a menu photo, clean catalog names and later explain sales/stock changes from cited merchant records. Show confidence or missing evidence, keep the operator in control of every write, and never infer settlement, inventory or profit from text alone. Meter usage server-side per account and plan before enabling paid models. Evaluate business value against manual setup time, correction rate, language quality, provider cost and privacy.
- Give agents a repeatable working contract: objective, in-scope files, source revision, evidence type, acceptance test and handoff. Keep `AGENTS.md` for durable repository rules and a small skill only for a proven repeatable workflow; do not create overlapping agents, prompts or tools as a substitute for shipping. REA answers packaged/runtime questions, source review answers source questions, and real-device QA answers device questions.

## Authority and safety

Proceed autonomously with source inspection, local fixes, documentation and authorized tests. Keep founder control over production promotion, live data changes, identity/access grants, credentials, spending, payments and customer or public contact. Never expose secrets, self-approve a protected change, invent a reviewer, bypass CI or imply that a preview is production. A broad desire to keep working does not expand the scope of a credential, provider, payment, customer or production action.

Routine scoped PR work is authorized, including a merge only when the applicable checks and eligible independent review actually pass. Do not weaken a ruleset or treat a Codex review as the required independent approval.

Use one accountable integration writer and serial heavy builds and tests. The owner has requested delegation: assign bounded, disjoint source slices or read-only reviews to agents, name their acceptance check, and review each handoff before integration. Do not create duplicate workers, unbounded fleets, or competing writes to one checkout. Preserve active servers and user-visible applications. Prefer existing approved tools and corporate records; do not start hourly tasks or paid model fallback without authorization.

SuperMega agent execution uses existing paid cloud/VPS capacity only. Local Ollama/inference and local-RAM readiness gates are retired; browser QA remains a separate acceptance stream. Do not provision new capacity or use metered model APIs without an explicitly authorized provider, task and spend ceiling.

## Evidence and release gates

For every acceptance claim, record `PASS`, `FAIL`, `BLOCKED` or `NOT RUN`, the exact source/build or target, and the evidence source. Local unit tests prove only their tested local contract. Build and artifact checks do not prove browser recovery. Preview behavior does not prove production. Hosted health does not prove founder sign-in, tenant isolation, persistence or customer use. A customer outcome requires actual customer acceptance.

Production release requires a clean exact-head candidate, passing required CI and security checks, independent eligible review, explicit release authority, reviewed migration and rollback scope, and post-release checks on canonical domains. If any gate is missing, continue useful source or test work and keep the gate open. Never mark the full objective complete while any required customer, technical, commercial or operational proof is missing.
