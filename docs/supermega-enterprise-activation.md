# >_ SuperMega managed-trial database activation

`app.supermega.dev` is an isolated, browser-local product demo until every managed-trial gate below passes. It does not use SQLite and it must not be represented as a customer system of record. The canonical managed backend is the private `app_private` schema in Supabase Postgres; browser code never receives its connection string or a service-role key.

The validator is intentionally read-only. It does not apply migrations, create users, provision workspaces, or enable writes.

## Local PostgreSQL 17 release gate

Run this first on a development machine with PostgreSQL 17 binaries, matching `psql`, `pg_dump`, and `pg_restore`, Psycopg 3, and OpenSSL:

```powershell
npm run database:postgres17:preflight
npm run database:postgres17:rehearse
npm run database:postgres17:record
npm run database:postgres17:record:verify
```

The runner accepts only executable paths, never database credentials. It creates two disposable PostgreSQL 17 clusters with generated in-memory secrets, TLS, and a `127.0.0.1` listener. The first cluster recreates the metadata-only legacy public catalog, applies the digest-bound public browser quarantine twice, applies all eleven migrations as `postgres`, carries representative v1 records through v10, provisions the exact runtime membership, and runs the production read-only validator. It proves that `anon` and `authenticated` retain no public relation or sequence privilege, future objects owned by either `postgres` or `supabase_admin` do not regain browser defaults, and the server-only contact path remains available. It also proves durable named-owner authorization, active Supabase-session acceptance, immediate denial after session deletion, an injected mid-activation failure with zero partial workspace writes, idempotent activation replay, and database-enforced suspension that blocks operational reads and writes even when a membership remains active. The broader suite covers identity locality, caller-only workspace discovery, tenant isolation, capability-scoped reads and writes, immutable events, approvals, product journeys, backup, and recovery. A second clean cluster restores the custom-format backup, revalidates schema version 10 and the runtime role, rechecks the public quarantine, verifies retained rows, and is removed with the first cluster.

The current sanitized proof is `hq/research/postgres17-rehearsal.json`. `database:postgres17:record` requires a clean worktree, reruns the complete disposable rehearsal, hashes the exact migrations, validator, runner, and managed Python runtime files, verifies the observed PostgreSQL archive, and atomically replaces the proof only after every check and cleanup gate passes. `hq:verify` fails when the recorded implementation digest becomes stale. The receipt records PostgreSQL 17.10, all passing checks, complete cleanup, and zero Supabase, Vercel, or production mutation without storing a URL or credential. This remains a repeatable local release gate, not hosted activation. It explicitly retains the isolated Supabase, Security Advisor, private Storage, transaction-mode pooler, and provider backup/recovery gates. PostgreSQL documents the [Windows binary distribution](https://www.postgresql.org/download/windows/), and Supabase documents its separate [local-development boundary](https://supabase.com/docs/guides/local-development/overview).

## One-time non-production proof

1. Record the protected production project's exact 20-character ref in `supermega.productionSupabaseProjectRef` in `package.json`, keep `supermega.productionSupabaseTargetStatus` at `protected-unapproved`, review both, and commit them before the rehearsal. The ref is an exclusion boundary, not activation approval: non-production preflight must reject it, while production handoff must remain impossible. The preflight rejects an unconfigured value or any uncommitted change to that file. A project ref is a public identifier, not a credential. If there is no known production project to protect, stop here rather than guessing a ref.
2. Create a Supabase branch or separate non-production project and confirm backup and restore responsibilities. Record its different 20-character ref. If a branch is used, remember that [custom roles are not captured when a branch is created](https://supabase.com/docs/guides/deployment/branching/dashboard), so this rehearsal must recreate and verify the SuperMega roles explicitly.

Before continuing, fetch reviewed `origin/main`, use a clean checkout at that exact commit, and prepare the non-mutating rehearsal packet before handling any database credential:

```powershell
git fetch origin main
npm run database:supabase:packet -- --target-project-ref <NON_PRODUCTION_PROJECT_REF> --output .tmp\supermega-supabase-rehearsal-packet.json
npm run database:supabase:packet:verify -- .tmp\supermega-supabase-rehearsal-packet.json
```

For an unpublished reviewed candidate, bind both commands to its current owner-review handoff receipt. This validates the exact candidate and current live/remote relationship; it does not approve a push, merge, deployment, provider mutation, or database write.

```powershell
npm run database:supabase:packet -- --target-project-ref <NON_PRODUCTION_PROJECT_REF> --release-handoff <SUPERMEGA-RELEASE-HANDOFF.json> --output .tmp\supermega-supabase-rehearsal-packet.json
npm run database:supabase:packet:verify -- .tmp\supermega-supabase-rehearsal-packet.json --release-handoff <SUPERMEGA-RELEASE-HANDOFF.json>
```

The packet rejects the protected production ref and any checkout that differs from `origin/main`. It binds the target to schema v10, the exact reviewed commit, all eleven ordered migration hashes, the public browser quarantine hash and source-audit hash, the backup/restore evidence contract, and the read-only preflight command. It contains no credential, enables no write, and cannot apply a migration. Regenerate it after any migration, public-catalog audit, or release change.

Supabase currently documents daily backups for Pro, Team, and Enterprise projects. Before the hosted rehearsal, confirm an actual backup exists for the source, record its non-secret identifier and time, and prove restoration to an isolated target. Physical backups do not preserve custom-role passwords, and database backups do not restore Storage objects; role-password recovery and private-object recovery therefore remain separate checks.

3. Download that project's CA certificate from the dashboard SSL Configuration panel and save it in an ignored local file such as `.tmp/supermega-rehearsal-ca.crt`. Save an administrative URL for the empty rehearsal target in `.tmp/supermega-rehearsal-admin-url.txt` with `sslmode=verify-full` and one URL-encoded `sslrootcert` value pointing to that reviewed CA. Prefer the [direct connection](https://supabase.com/docs/guides/database/connecting-to-postgres) on port `5432`; on an IPv4-only machine, the shared session pooler on port `5432` is accepted. The transaction-mode pooler on port `6543` is for serverless runtime traffic and is deliberately rejected for migrations. Never put a database URL in a command argument, source file, issue, task, or chat. Supabase documents that [`verify-full` verifies both the CA and hostname](https://supabase.com/docs/guides/platform/ssl-enforcement), while `require` encrypts without authenticating either.
4. Before applying SQL, bind the URL to the explicit non-production ref and run the clean-target preflight:

```powershell
npm run database:supabase:preflight -- -DatabaseUrlFile .tmp\supermega-rehearsal-admin-url.txt -ExpectedProjectRef <NON_PRODUCTION_PROJECT_REF> -SslRootCertFile .tmp\supermega-rehearsal-ca.crt
```

The preflight is read-only and fail-closed. It requires PostgreSQL 17, hostname-verified TLS, a stable administrative session with permission to create the private schema and runtime role, the `postgres` database, and a target where both `app_private` and `supermega_trial_backend` are absent. It rejects the reviewed production ref, a mismatched Supabase URL, a non-Supabase host, unreviewed production-target configuration, and a transaction-pooler migration URL. Its sanitized JSON includes the non-secret target project ref so the evidence can be matched to the next migration step. It does not apply a migration, alter Supabase, publish a secret, or touch Vercel.
5. Apply the migrations in filename order: `20260722004500_private_trial_backend_role_preflight.sql`, `20260722005134_private_trial_backend_foundation.sql`, `20260722142801_private_trial_backend_v2.sql`, `20260723094500_private_trial_backend_v3_website.sql`, `20260723144500_private_trial_backend_v4_hardening.sql`, `20260724204920_private_trial_backend_v5_read_capabilities.sql`, `20260730113000_private_trial_backend_v6_managed_activation.sql`, `20260730123000_private_trial_backend_v7_workspace_discovery.sql`, `20260802161500_private_trial_backend_v8_rls_initplan.sql`, `20260803063822_private_trial_backend_v9_metadata_rls.sql`, and `20260804102000_private_trial_backend_v10_supabase_session_revocation.sql`. Use the same reviewed administrative migration target; confirm that its project ref matches both the packet and preflight JSON before proceeding. Never edit or replay a historical migration, and never use the application runtime login for migrations. Runtime readiness requires schema version 10. Version 6 adds immutable workspace activation identity and active-workspace gates. Version 7 adds caller-only named-user company discovery. Version 8 evaluates request context once per query for the Supabase RLS InitPlan performance contract. Version 9 enables defense-in-depth RLS on schema metadata and grants its one filtered read policy only to the backend role. Version 10 keeps its boolean-only session check in the private schema, grants it only to the server runtime role, and denies managed access immediately when the signed Supabase session no longer exists. Historical workspaces remain suspended until explicitly re-authorized.
6. Only after all migrations pass, create the distinct `supermega_trial_runtime` login role with a password-manager-generated secret and `LOGIN INHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`. Grant `supermega_trial_backend` to it with `INHERIT TRUE`, `SET FALSE`, and no admin option. The backend group must have exactly that one runtime member, and the runtime login must have exactly that one parent and no members of its own. Give the login no direct grants, default grants, role settings, or object ownership. Production Vercel must use the shared transaction-pooler username `supermega_trial_runtime.<project-ref>`; privileged `postgres.<project-ref>` credentials are rejected.
7. Use a TLS connection URL for that login. For Vercel serverless traffic, use the Supabase transaction-mode pooler and append `sslmode=require` (or a stronger provider-supported verification mode). The runtime explicitly disables autocommit, wraps each identity-bearing operation in one transaction, uses transaction-local workspace and actor settings, and disables Psycopg prepared statements for transaction-pool compatibility.
8. Configure Supabase Auth for named, non-anonymous users. Create the trial owner's account through the approved Auth administration flow and record its UUID; this exact UUID becomes `ownerActorId` in the activation plan and must match `auth/v1/user` at sign-in. Retrieve an enabled modern `sb_publishable_...` key and save it in an ignored file such as `.tmp/supermega-nonproduction-publishable-key.txt`. The publishable key is intentionally browser-visible and is not an authorization grant; private workspace membership and forced RLS remain the authority. Do not use a service-role key, legacy anon key, user metadata, or a client-asserted role. `SUPERMEGA_TRIAL_IDENTITY_SECRET` is optional and is allowed only when an actual trusted server gateway signs the complete v2 identity envelope.
9. Export `supermega.managed_trial_request.v1` from Settings after the named workspace has product records, behavior signals, owner-reviewed decisions, and a saved trial plan. Compile it into a seven-day, target-bound activation plan. The compiler retains only evidence counts and digests, binds the SHA-256 fingerprint of the reviewed administrative CA, derives least-privilege owner capabilities from the selected product, rejects embedded credentials, and derives one deterministic compensation authorization that can only suspend access after a downstream release-gate failure while retaining customer data:

```powershell
uv run python -m supermega_runtime.managed_activation prepare --request-file .tmp\managed-trial-request.json --workspace-id <WORKSPACE_ID> --owner-actor-id <SUPABASE_AUTH_USER_UUID> --approval-id <REVIEWED_APPROVAL_ID> --approved-by <NAMED_OWNER> --approved-at <UTC_ISO_TIMESTAMP> --project-ref <NON_PRODUCTION_PROJECT_REF> --release-commit <EXACT_REVIEWED_COMMIT> --admin-ca-file .tmp\supermega-rehearsal-ca.crt --output .tmp\managed-activation-plan.json
```

For a client with one or more purchased products, bind the verified private preparation, the per-product portal recipes, every exact managed-trial request, and the current managed activation plan into one tenant activation manifest. Repeat `--managed-request` in canonical product order (`shop`, `plant`, `website`, `ecommerce`) and include only products present in the portal bundle:

```powershell
npm run client:portal:prepare -- --preparation .tmp\client-preparation.json --output .tmp\client-portal-bundle.json
npm run client:portal:verify -- --bundle .tmp\client-portal-bundle.json --preparation .tmp\client-preparation.json
npm run client:portal:bind -- --bundle .tmp\client-portal-bundle.json --preparation .tmp\client-preparation.json --activation-plan .tmp\managed-activation-plan.json --managed-request .tmp\shop-request.json --managed-request .tmp\website-request.json --managed-request .tmp\ecommerce-request.json --output .tmp\client-portal-activation.json
npm run client:portal:activation:verify -- --manifest .tmp\client-portal-activation.json --bundle .tmp\client-portal-bundle.json --preparation .tmp\client-preparation.json --activation-plan .tmp\managed-activation-plan.json --managed-request .tmp\shop-request.json --managed-request .tmp\website-request.json --managed-request .tmp\ecommerce-request.json
```

The manifest is a no-write handoff, not activation. It fails closed if the workspace, named owner, product set, product order, template, source-request digest, recipe plan, setup route, release target, or custom-extension policy drifts. It retains the executable managed activation plan, binds one owner membership to the exact purchased products, preserves Ecommerce's Shop-backed commerce surface without granting Ecommerce to Shop-only tenants, and performs no tenant, provider, deployment, message, or production write.

10. Save the non-production runtime URL in an ignored local file such as `.tmp/supermega-nonproduction-database-url.txt`. Save a separate least-privilege, read-only catalog URL for the same project's Storage audit in `.tmp/supermega-nonproduction-storage-audit-url.txt`. Retain the administrative migration URL in `.tmp/supermega-rehearsal-admin-url.txt` only for the bounded membership operation. All URLs must identify the same explicit project ref; the activation validator rejects cross-project evidence, non-Supabase hosts, URL-level routing overrides, unbound pooler usernames, and the transaction-mode pooler for administrative activation. Never pass a database URL directly on the command line.
11. Run the read-only database, browser-auth, activation-plan, and workspace-state audit:

```powershell
powershell -ExecutionPolicy Bypass -File tools/activate_supermega_database.ps1 -DatabaseUrlFile .tmp\supermega-nonproduction-database-url.txt -StorageAuditDatabaseUrlFile .tmp\supermega-nonproduction-storage-audit-url.txt -AdminDatabaseUrlFile .tmp\supermega-rehearsal-admin-url.txt -SupabasePublishableKeyFile .tmp\supermega-nonproduction-publishable-key.txt -ActivationPlanFile .tmp\managed-activation-plan.json -ExpectedProjectRef <NON_PRODUCTION_PROJECT_REF> -ValidateOnly
```

The audit must prove PostgreSQL major 17, encrypted read-only transport, exact role-membership edges, no runtime or backend role settings, no transitive runtime members, trusted ownership, the exact private schema version, forced RLS, exact grants and applicable default ACLs, browser-role isolation, complete policy and security-constraint fingerprints, exact trigger events, structure and function bodies, exact indexes, an enabled modern browser publishable key, and a vacant or exact-replay workspace identity. Run Supabase Security Advisor after the migration and resolve every applicable finding. Exercise cross-workspace denial, access revocation, duplicate policy names, inverted or swapped identity predicates, trigger `WHEN` bypasses, global/default grants, mismatched approval event/surface combinations, immutable events, optimistic concurrency, backup, and restore on non-production data. PGlite and the local PostgreSQL 17 gate are strong preflight evidence but do not replace this hosted PostgreSQL 17 proof.

The latest protected-project metadata snapshot is `hq/readiness/supabase-security-advisor-audit.json`. It records only Security Advisor and PostgreSQL catalog facts, no business rows or credentials. The current snapshot is blocked: 27 legacy `public` tables are default-denied by RLS because they have no policies, but `anon` and `authenticated` still retain broad table grants; two public sequences retain browser grants; and default privileges owned by both `postgres` and `supabase_admin` can grant future tables, sequences, and routines back to browser roles. The same read-only audit found zero public views, materialized views, foreign tables, or routines. Do not add permissive policies or modify production to silence the informational lint. Supabase treats Data API grants and RLS as separate controls, so both must be deliberate ([Securing your API](https://supabase.com/docs/guides/api/securing-your-api), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)).

Before any production proposal, use an owner-approved isolated clone of the protected schema. Verify that its relation, sequence, routine, and default-ACL inventory still exactly matches the signed audit; then apply `supabase/rehearsal/20260804_public_browser_quarantine.sql` through the reviewed administrative migration session. The script fails before mutation on any catalog drift, is idempotent, revokes public/`anon`/`authenticated` object and future-object defaults, and preserves the existing server-side contact path. Prove all three packet requirements: browser table-and-sequence denial, default-grant denial for both owners, and retained server access. Then apply v8 through v10, rerun Security Advisor and the exact metadata queries, test active and revoked sessions, exercise backup and restore, and verify the refreshed digest. The local compatibility gate is `npm run database:public-browser-quarantine:verify`; it is evidence preparation, not hosted activation.

12. Exchange a fresh named-owner Supabase access token for one durable v2 approval packet before applying the plan. That packet includes the exact automatic-compensation authorization. Then apply it on non-production, verify named-user sign-in and all selected product flows, and exercise the non-destructive compensation path. Authorization, activation, and compensation are idempotent; replay never creates a second authorization, membership, access gate, or event. Receipt files are explicitly non-authoritative local projections; the immutable PostgreSQL event must be requeried before a receipt is trusted:

```powershell
uv run python -s -m supermega_runtime.managed_activation authorize --plan-file .tmp\managed-activation-plan.json --database-url-file .tmp\supermega-rehearsal-admin-url.txt --confirm-owner-approval <REVIEWED_APPROVAL_UUID> --owner-access-token-file .tmp\named-owner-access-token.txt --publishable-key-file .tmp\supermega-nonproduction-publishable-key.txt --decision-note "Owner approved this exact plan and release."
```

## Production handoff

1. Repeat migration, Security Advisor, backup/restore, named-user Auth, and read-only activation-plan audits against the approved production project while the live app remains `isolated_demo`. Compile a new plan from the exact release commit and production project ref; never reuse the non-production plan.
2. Run the guarded production handoff. It verifies the named owner with Supabase Auth, stores the durable authorization packet, verifies the effective Vercel project is still isolated, and stages the database and browser-safe authentication values without enabling writes. It then atomically inserts one active workspace gate, the owner membership, and the immutable activation event. `SUPERMEGA_TRIAL_WRITES_ENABLED=true` is written last. Any failure removes only values created by that attempt and suspends an already-activated workspace without deleting customer data:

```powershell
powershell -ExecutionPolicy Bypass -File tools/activate_supermega_database.ps1 -DatabaseUrlFile .tmp\supermega-production-database-url.txt -StorageAuditDatabaseUrlFile .tmp\supermega-production-storage-audit-url.txt -AdminDatabaseUrlFile .tmp\supermega-production-admin-url.txt -SupabasePublishableKeyFile .tmp\supermega-production-publishable-key.txt -OwnerAccessTokenFile .tmp\named-owner-access-token.txt -ActivationPlanFile .tmp\managed-production-activation-plan.json -ActivationReceiptFile .tmp\managed-production-activation-receipt.json -ExpectedProjectRef <REVIEWED_PRODUCTION_PROJECT_REF> -ProductionHandoff -ApprovalId <REVIEWED_APPROVAL_UUID>
```

`-Replace` is deliberately rejected. Credential rotation is a separate reviewed recovery operation. The wrapper refuses authorization or activation unless the target matches the committed production ref, the activation plan is current, the checkout is clean, `HEAD` equals freshly fetched `origin/main`, canonical live release metadata serves that exact commit, `-ProductionHandoff` is explicit, hostname-verified administrative TLS uses the CA fingerprint bound into the plan, and the approval UUID matches the plan. It binds Vercel CLI operations to the canonical app project ID and organization ID instead of accepting a project name from the command line. If the apply subprocess fails after committing but before writing its local projection, the wrapper uses the command's mutation signal and requeries PostgreSQL before compensating an active gate. The exact durable compensation command remains available even if `origin/main` or the live alias advances during recovery; mutable release provenance cannot strand an active workspace. Do not deploy a partially configured environment.

3. Redeploy the exact reviewed `megaos` commit through the guarded coordinated workflow. The Vercel environment verifier must reject any alleged managed mode missing `SUPERMEGA_DATABASE_URL`, `SUPERMEGA_TRIAL_WRITES_ENABLED`, `VITE_SUPABASE_URL`, or `VITE_SUPABASE_PUBLISHABLE_KEY`. A server-only gateway secret is optional and never substitutes for the browser's real named-user sign-in path.
4. Require `/api/health` to report `operating_mode=managed_trial`, `enterprise_db_ready=true`, `security_ready=true`, and all activation steps ready. Sign in through the actual production UI as the exact owner UUID, create the selected product's first managed state, reload it, verify the immutable event, and prove a different workspace and user receive no rows.
5. Pass the Commerce, Production, Website, company, setup, isolation, revocation, failure, recovery, context-retention, and baseline-change journeys. Approval requests must use `decision_packet.v1`; service and agent actors cannot make terminal approvals, approve Website releases, or retain owner-only AI context. No scheduler, external message, payment, stock movement, production command, domain publish, CRM write, or model training is enabled by workspace activation.
6. Record Founder and customer trial-owner acceptance against the requeried PostgreSQL activation event, its matching local receipt projection, and exact live release metadata. Only then onboard customer data and begin the bounded paid pilot.

If any gate fails, keep or restore `isolated_demo`, do not redeploy partial environment variables, suspend the workspace membership, and do not describe the workspace as activated. The helpers emit sanitized JSON evidence, never print database URLs or keys, and send production values to Vercel through standard input.
